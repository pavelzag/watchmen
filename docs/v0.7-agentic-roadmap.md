# Watchmen v0.7.0 Agentic Roadmap

Status: In progress

Implemented so far:

- Agent run/step audit tables and first-party agent runtime.
- Flow 1 initial slice: read-only finding investigation from the Findings page.
- Flow 2 initial slice: approval-required remediation planning from the Findings page, with GCP handoff to the existing Terraform PR workflow.
- Flow 3 initial slice: verification from the Task Center against the latest GCP/AWS snapshots.

v0.7.0 focuses on turning Watchmen's existing cloud scans, findings, compliance checks, attack paths, task center, and Terraform remediation flows into guided security operations workflows.

The goal is not to add a generic chatbot. The goal is to let a user ask Watchmen to investigate, plan, and verify security work using bounded tools over data Watchmen already owns.

## Product goals

- Reduce the time from finding discovery to a clear remediation decision.
- Explain risk in terms of reachable resources, affected identities, compliance impact, and infrastructure ownership.
- Create auditable remediation plans before any destructive or cloud-mutating action.
- Reuse existing Watchmen primitives: snapshots, findings, compliance controls, attack paths, GitHub/Terraform tasks, request logs, and scan coverage warnings.
- Keep provider flexibility across Claude, Gemini, and OpenAI without binding the product to one agent framework.

## Recommended architecture

Start with a small first-party agent runtime around the existing provider-agnostic AI client instead of committing immediately to LangChain.

LangChain can still be evaluated for tracing, tool routing, memory, or multi-step graph orchestration, but v0.7.0 should keep the core contracts simple:

- `AgentRun`: persisted execution record with user, prompt, status, selected workflow, timestamps, and final answer.
- `AgentStep`: ordered tool calls, inputs, summarized outputs, errors, and approval requirements.
- `AgentTool`: typed server-side functions with explicit input schemas, scoped permissions, and deterministic return objects.
- `AgentPolicy`: guardrails for read-only tools, approval-gated write tools, cloud mutation restrictions, and provider data boundaries.

Initial tool categories:

- Inventory tools: latest GCP/AWS snapshot, resource lookup, owner/tag lookup, scan coverage.
- Finding tools: finding lookup, severity grouping, related findings, historical diff.
- Compliance tools: affected SOC 2 / ISO 27001 controls, failed control grouping, risk acceptance state.
- Attack path tools: path lookup, external exposure, identity/resource reachability.
- Evidence tools: auth failures, request logs, agent event summaries, CloudTrail/Cloud Logging summaries where available.
- Remediation tools: Terraform target lookup, patch preview, PR creation, rescan/verification.

## Flow 1: Investigate finding

User value:

Security and platform teams can ask why a finding matters and get an evidence-backed explanation instead of reading isolated rule output.

Example prompts:

- "Why is this S3 bucket critical?"
- "Can this public GKE service reach customer data?"
- "What changed since the last scan for this finding?"

Scope:

- Add an `investigate_finding` workflow that accepts a finding ID or natural-language reference.
- Gather the finding, affected resource, cloud/account/project, related IAM principals, public exposure, attack paths, compliance controls, scan age, and relevant recent auth/request evidence.
- Produce a structured answer with:
  - risk summary
  - evidence
  - affected resources and principals
  - compliance impact
  - confidence and missing data
  - suggested next action
- Link each evidence item back to an existing Watchmen page where possible.

Implementation tasks:

- Add typed agent tools for finding lookup, resource lookup, related compliance controls, attack path lookup, and request/auth evidence summaries.
- Add `app/api/agent/investigate-finding` as a streaming route using NDJSON or SSE, matching the existing task center streaming style.
- Add a "Investigate" action to finding detail views and result cards.
- Store agent runs and steps in Postgres for auditability and later replay.
- Add tests for tool input validation, missing-resource handling, and deterministic evidence assembly.

Done when:

- A user can start from a finding and receive a multi-step investigation with cited Watchmen evidence.
- The workflow handles missing credentials, stale scans, and partial scan coverage without hallucinating.
- No cloud mutation or PR creation is possible from this flow.

## Flow 2: Plan remediation

User value:

Users can turn a confirmed issue into a safe, reviewable remediation plan that respects ownership, tags, provider boundaries, and Terraform state.

Example prompts:

- "Plan a fix for all public non-production storage buckets."
- "Fix this security group but do not touch customer-facing workloads."
- "Generate a Terraform PR for the safest fix."

Scope:

- Add a `plan_remediation` workflow that can start from a finding, a group of findings, or a natural-language objective.
- Produce a staged plan before generating code:
  - target resources
  - excluded resources and why
  - risk reduction
  - expected compliance impact
  - proposed Terraform or CLI approach
  - rollback notes
  - required approvals
- Integrate with the existing Terraform preview and PR task center flows.
- Require explicit user confirmation before PR creation or any future cloud-mutating action.

Implementation tasks:

- Add typed tools for Terraform target discovery, remediation target selection, patch preview, and existing GitHub PR creation.
- Add an approval checkpoint between plan generation and PR creation.
- Add a remediation plan UI panel with selected resources, excluded resources, generated diff summary, and approval controls.
- Extend task center task types to distinguish `agent_remediation_plan`, `terraform_preview`, and `terraform_pr`.
- Add regression tests for resource exclusion rules, provider scoping, and approval enforcement.

Done when:

- A user can generate a remediation plan from one or more findings.
- Watchmen can preview a Terraform patch and open a PR only after explicit confirmation.
- The plan clearly lists what it will not change.

## Flow 3: Verify fix

User value:

Users can confirm that a remediation actually closed the issue instead of manually comparing scans and compliance pages.

Example prompts:

- "Did the PR fix the public bucket finding?"
- "Rescan and verify whether SOC 2 improved."
- "What findings remain after this remediation?"

Scope:

- Add a `verify_fix` workflow that connects a remediation plan or PR to a fresh scan and compares before/after state.
- Produce a verification report:
  - resolved findings
  - unchanged findings
  - new findings
  - compliance score/control changes
  - scan coverage caveats
  - recommended follow-up

Implementation tasks:

- Add tools for loading previous agent runs, triggering GCP/AWS scans through existing scan routes, comparing snapshots, and comparing compliance results.
- Add verification run output to the task center.
- Add a "Verify" action to completed remediation tasks and Terraform PR task results.
- Persist before/after finding IDs and compliance summaries on the agent run.
- Add tests for before/after diffing and scan failure reporting.

Done when:

- A user can verify a completed remediation against a new scan.
- Watchmen reports resolved, remaining, and newly introduced risk without requiring manual page-by-page comparison.
- Partial scan failures are visible in the verification report.

## Safety and trust requirements

- Default all agent tools to read-only.
- Require explicit user approval for PR creation and any future cloud mutation.
- Keep all agent tool outputs structured and bounded before sending them to an AI provider.
- Show missing data and stale scan age as first-class output.
- Persist tool steps for auditability, but avoid storing raw secrets or full credential material.
- Treat generated remediation as advisory until reviewed through Terraform preview or PR diff.
- Prefer deterministic Watchmen data over model-generated assumptions.

## v0.7.0 milestone sequence

1. Agent foundation: database tables, run/step types, tool schema pattern, streaming route helper, provider boundary documentation.
2. Investigation workflow: read-only tools, finding detail integration, audit trail, tests.
3. Remediation planning workflow: target selection, plan UI, Terraform preview integration, approval checkpoint.
4. PR execution integration: connect approved plans to existing GitHub/Terraform PR task flow.
5. Verification workflow: rescan trigger, before/after diff, compliance delta, task center action.
6. Hardening: prompt-injection checks, missing-data handling, stale scan warnings, event logging, regression tests.
7. Documentation: user guide updates, architecture diagram updates, demo script, and limitations.

## Out of scope for v0.7.0

- Autonomous cloud mutation without human approval.
- Long-running background agents that act without a user-initiated run.
- Full incident response automation.
- Replacing the current query assistant.
- Committing to LangChain unless the prototype proves it reduces complexity for Watchmen's actual workflows.

## Success metrics

- A finding investigation returns useful evidence in under 30 seconds for fixture data.
- A remediation plan can produce a Terraform preview for supported GCP/AWS finding types.
- Verification can identify resolved versus remaining findings after a fresh scan.
- Every agent run has an auditable step trail.
- No write action can happen without an explicit user approval event.
