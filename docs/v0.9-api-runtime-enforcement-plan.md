# Watchmen v0.9: API and Runtime Enforcement Plan

## Goal

Watchmen v0.9 should move runtime security from dashboard-first detection toward an API-first platform with enforceable request/runtime policies.

The release should concentrate on:

- Authenticated Watchmen API access to data gathered by Watchmen.
- Runtime request data exposed through stable API endpoints.
- Runtime alerting and blocking rules that can be created, fetched, updated, and tested through the API.
- A test suite that simulates request events and verifies, through the Watchmen API, that matching traffic was alerted or blocked.

## API-First Direction

The Watchmen API should be the source of truth for product integrations, tests, dashboard views, CLIs, and future agentic workflows.

Suggested route shape:

```text
/api/watchmen/v1/runtime/requests
/api/watchmen/v1/runtime/requests/:id
/api/watchmen/v1/runtime/rules
/api/watchmen/v1/runtime/rules/:id
/api/watchmen/v1/runtime/alerts
/api/watchmen/v1/runtime/summary
```

Runtime request endpoints should support filters such as:

```text
from / to
decision=allow|flagged|would_block|blocked
method=GET|POST|DELETE
pathPrefix=/admin
sourceIp=
sourceIpClass=public|private
statusCode=
ruleId=
limit / cursor
sort=
```

Rule endpoints should support:

```text
GET    list rules
POST   create rule
PATCH  update rule
DELETE delete rule
```

## MCP and Agentic Data Gathering

MCP should be treated as an optional agent-facing adapter, not as the core product API.

Recommended architecture:

```text
Watchmen database / rule engine
        |
Watchmen REST API
        |
Dashboard, tests, CLI, external integrations
        |
Optional MCP server for agentic workflows
```

An MCP server can expose Watchmen operations as tools an AI agent can call, for example:

- List runtime requests from the last hour.
- Summarize would-block events by rule.
- Create or update a runtime rule.
- Fetch request evidence for an alert.
- Query attack-vector matches.

The MCP server should call the Watchmen API rather than bypassing it.

## Runtime Rule Model

The current rule model supports `flag` and `would_block`. v0.9 should reduce ambiguity by introducing an explicit enforcement mode.

Recommended decision values:

```text
allow
flagged
would_block
blocked
```

Recommended rule shape:

```text
action: alert | block
mode: detect | enforce
```

Behavior:

- Alert rules produce `flagged`.
- Block rules in detect mode produce `would_block`.
- Block rules in enforce mode produce `blocked` and return a blocking response, such as HTTP 403.

## Rule Conditions and Attack Vectors

Start with the existing rule conditions:

```text
method
path_prefix
content_type
body_contains
source_ip_class
```

For v0.9, consider adding:

```text
path_regex
status_code
known_attack_vector
```

Known attack vectors should be implemented as rule templates rather than hidden hardcoded behavior.

Initial templates:

```text
admin_path_probe       /admin, /wp-admin, /phpmyadmin
path_traversal         ../, %2e%2e
sql_injection_probe    union select, ' or 1=1
rce_probe              /cgi-bin, ${jndi:, ;wget, ;curl
sensitive_file_probe   /.env, /etc/passwd, /config.json
destructive_method     DELETE, PUT, PATCH
```

## Enforcement Strategy

### Phase 1: Watchmen-Controlled Request Paths

Add real blocking where Watchmen already controls request flow:

- `/api/proxy`
- `/api/trace`

Flow:

```text
normalize incoming request
load enabled rules
evaluate rules
if block rule matches and enforcement is enabled:
  save runtime event as blocked
  return 403
else:
  forward/process request
  save allow/flagged/would_block event
```

This provides a practical enforcement baseline for demos, tests, and Watchmen-routed traffic.

### Phase 2: Kubernetes Inline Enforcement

For real cluster-wide HTTP blocking, add an inline enforcement component rather than extending the current eBPF tracer into a full HTTP WAF.

Preferred approaches:

- Ingress external-auth service.
- Envoy/Istio external authorization.
- Watchmen enforcement gateway.

The current eBPF agent should remain primarily a sensor. It is well suited for observing traffic and can potentially support coarse IP/port-level enforcement later, but HTTP verb/path/body enforcement is better handled at an HTTP-aware inline point.

## Test Suite

The v0.9 test suite should verify enforcement through the Watchmen API.

Required cases:

- Rule CRUD through the Watchmen API.
- Runtime request ingestion and listing through the Watchmen API.
- Detect-mode block rule records `would_block`.
- Enforce-mode block rule returns `403`.
- Blocked request is persisted.
- Alerts endpoint reports matched rule, severity, and reason.
- Nonmatching requests remain allowed.

Example blocked-path scenario:

```text
Create rule:
  action: block
  mode: enforce
  condition: path_prefix /admin

Send request:
  GET /admin/users

Expect:
  HTTP 403
  runtime event decision = blocked
  matchedRuleIds contains created rule
  /api/watchmen/v1/runtime/requests returns the event
```

Example alert-only scenario:

```text
Create rule:
  action: alert
  condition: method DELETE

Send request:
  DELETE /api/users/123

Expect:
  request is not blocked
  runtime event decision = flagged
  alert appears through API
```

## Suggested Implementation Order

1. Add Watchmen API authentication for scoped API keys or tokens.
2. Add `/api/watchmen/v1/runtime/requests`.
3. Add `/api/watchmen/v1/runtime/rules`.
4. Extend decisions with `blocked`.
5. Add explicit `mode: detect | enforce`.
6. Enforce block rules in `/api/proxy` and `/api/trace`.
7. Add attack-vector rule templates.
8. Add API integration tests for alerting and blocking.
9. Add optional MCP server as an adapter over the Watchmen API.
