# Watchmen v0.10: Shirudo Live-Shield Rollout Plan

Status: **Completed (`v0.10.0` Phases 1–3 implemented)**

## Versioning Decision: Why `v0.10.0` (Not `v1.0.0`)

Watchmen targets **v0.10.0** for the Shirudo integration rather than **v1.0.0**:

1. **Shirudo is currently pre-release:** Production Shirudo targets require a custom-patched `bpf-next` Linux kernel (signed-loader ABI, `tpm_command` and `mm_read_access` LSM hooks, `CONFIG_CRYPTO_MLDSA`), `systemd` 256+ UKI boot, and TPM 2.0. Standard GKE, Cloud Run, and stock cloud Linux VMs cannot run Shirudo enforcement without custom images.
2. **Watchmen `v0.9.0` baseline still has open GA items:** In `docs/v0.9-api-runtime-enforcement-plan.md`, Phase 2 (Kubernetes inline enforcement gateway) remains future work.
3. **Preserving `v1.0.0` for GA:** `v0.10.0` lets Watchmen ship and market the OpenAI + Cisco Shirudo integration immediately while reserving `v1.0.0` for full production GA.

---

## Core Architectural Guardrails

- **Opt-in by design:** Watchmen's existing agentless cloud posture scanning, Trivy container scanning, and `services/ebpf-agent` sensor remain the default for standard startups on Vercel, Cloud Run, GKE, EKS, and stock VMs.
- **Operator signing boundary:** Watchmen never stores or touches private ML-DSA-87 signing keys. Shield generation, compilation (`shirudo build` / `shirudo bpm build`), and signing (`shirudo bpm push`) happen on the customer's operator host or CI/CD runner via Watchmen CLI Handoff (`scripts/watchmen-cli.mjs`) and MCP (`/api/mcp`).
- **Human-approved rollout:** Coding agents (OpenCode, Claude Code, Codex) write and validate the `upatch` + exploit reproducer in a Shirudo test VM, then stop for explicit operator approval before signing and publishing to an OCI registry.

## 3-Phase Rollout

### Phase 1: Shirudo Auto-Shield via CLI Handoff (`v0.10` Slice 1 — Implemented)

Goal: Turn Watchmen container CVEs and live runtime attack alerts into ready-to-build Shirudo `upatch` / `Beefile` tasks for OpenCode, Claude Code, and Codex with zero new server infrastructure.

- **Handoff Schema (`lib/handoff/tasks.ts`, `lib/handoff/shirudo.ts`):**
  - Added `HandoffRemediationMode` (`"iac" | "shirudo_shield"`).
  - Added `"runtime_alert"` issue normalization (`handoffIssueFromRuntimeAlert`) from `RuntimeRequestEvent` + matched `RuntimeSecurityRule`s.
  - Namespaced `shirudo_shield` task fingerprints (`v0.10:shirudo_shield:...`) so shield tasks do not collide with IaC/Dockerfile PR tasks for the same CVE.
  - Added Shirudo-specific prompt & `Beefile` scaffold generation (`renderShirudoShieldInstructions`, `buildShirudoBeefileTemplate`), selecting between BPF C `upatch` and Java agent `upatch` strategies.
- **API & Storage (`app/api/handoff/tasks/route.ts`, `lib/handoff/store.ts`):**
  - `POST /api/handoff/tasks` accepts `remediationMode: "iac" | "shirudo_shield"` and persists it inside `payload`.
- **Dashboard UI:**
  - `components/PushToCliModal.tsx`: Added Remediation Mode switcher (`IaC / Code Fix` vs `Shirudo Live Shield (upatch)`) with `defaultRemediationMode` support and operator key-boundary notice.
  - `app/dashboard/trace/RuntimeSecurityPanel.tsx`: Added **Shield Alerts (CLI)** on the Alerts tab and **Shield with Shirudo (CLI)** inside the event detail modal.
  - `app/dashboard/container-scan/page.tsx`: Added **Shield (Shirudo)** triggers alongside **Send to CLI** for container CVEs.
  - `components/CliHandoffQueue.tsx`: Displays a `SHIRUDO SHIELD` badge on shield tasks in `/dashboard/tasks`.

### Phase 2: OTLP Telemetry Ingest & "Shielded" CVE Badges (Implemented)

Goal: Let Shirudo-protected Linux nodes report keepalives, tamper alerts, and blocked-attack counters back to Watchmen, and surface runtime mitigation status on CVEs and compliance controls.

- **OTLP/HTTP Ingest Endpoints:**
  - Add `/api/ingest/shirudo/v1/logs` and `/api/ingest/shirudo/v1/metrics` (with OTel Collector / Go reverse proxy front-end for hybrid PQC TLS `X25519MLKEM768` or `tls.classical_hosts` config).
  - Parse `shirudo.keepalive` (`verdict`, `tamper`, `integrity`, `kernel_release`, `image_root`, loaded `upatches`, `shirudo.quote`) and `shirudo.bpf.map.snapshot` (hit counts and `kernel-obs` events).
- **Postgres Schema (`lib/db.ts`):**
  - `shirudo_nodes`: latest node verdict, TPM attestation key (`ak_name`), kernel/image metadata, and active `upatches`.
  - `shirudo_upatch_fixes`: links `upatch_id` to CVE/advisory IDs (populated from signed tree publications or operator mapping).
  - `shirudo_shield_hits`: aggregated exploit-block counters mapped into Watchmen Runtime Security & Live Trace.
- **Shield-Aware Exposure & Compliance:**
  - Enrich Container Scan (`app/dashboard/container-scan/page.tsx`), Findings (`lib/findings.ts`), and SOC 2 / ISO 27001 controls with a `Shielded at Runtime` badge and compensating-control export evidence.
  - Extend `lib/handoff/verify.ts` (`watchmen_verify_task`) so `shirudo_shield` tasks verify against `shirudo_nodes` active upatch state.

### Phase 3: Enterprise Hardened VM Blueprints & Remote TPM Attestation (Implemented)

Goal: Provide turnkey infrastructure and cryptographic attestation for regulated/enterprise workloads.

- **Native Cryptographic TPM 2.0 Quote Verifier (`lib/shirudo/tpm-verify.ts`):**
  - Parses TPM 2.0 `TPMS_ATTEST`, `TPMT_SIGNATURE` (ECDSA SHA-256), and `TPMT_PUBLIC` (ECC NIST P-256) directly in Node.js `crypto`, verifying `extraData === SHA256(keepaliveBody)` and detecting monotonic `(resetCount, clock)` replay/rollback contradictions (`history_contradiction`).
- **Remote TPM Challenge Attestation (`app/api/shirudo/attest/route.ts`, `components/ShirudoFleetPanel.tsx`):**
  - Issues fresh 32-byte nonces (`shirudo attest --nonce=<hex>`), verifies signed TPM quote responses, and displays `TPM Verified` / `Replay / Rollback` status badges per node.
- **Enterprise Infrastructure Blueprints (`scripts/shirudo/`):**
  - Added OpenTelemetry Collector PQC TLS config (`scripts/shirudo/otel-collector-shirudo.yaml`) and Shielded GCE vTPM Terraform module (`scripts/shirudo/terraform/gcp-shirudo-vm/`).
